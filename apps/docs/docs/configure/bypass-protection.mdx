Keep DNS queries from selected client interfaces on paths that Sinkhole can inspect. Every protection is off by default, no interface is selected by default, and an upgrade doesn't enable a protection or list.

## Choose the Interfaces \{#choose-the-interfaces}

Open **Firewall → Sinkhole → Bypass** and select **Apply to** interfaces before enabling a protection. This selection belongs to **Global** and decides where Global's settings apply. Protections inspect only traffic arriving from clients on those interfaces; they don't affect the firewall's own lookups or outbound traffic.

Network and device matching uses those interfaces' current subnets, just like ordinary Sinkhole scopes. A client outside the selected subnets receives no Bypass DNS answer.

## Set Protections per Network and Device \{#set-protections-per-network-and-device}

The row under the tabs chooses what you edit: **All**, **Global**, one network, or one device. The line under it names the clients those settings apply to. Each choice shows only its own settings; settings from a broader choice are never shown.

A client follows the most specific settings that exist: its device's first, then its network's, then Global's. A network or device that is turned off on the Clients tab is skipped.

**Global** alone holds:

- **Apply to** interfaces.
- **Plain DNS** redirect and its exemptions.

A network or device also holds **Enable**, which turns its protections on.

Global and each network or device hold:

- **Bypass Lists**, the enabled sources it uses. Sources are added, enabled, and updated on [Lists → Bypass](/docs/configure/lists#add-bypass-lists). With no enabled source, the field shows one line with an **Open Lists** link instead.
- The encrypted-DNS settings, **Discovery**, the tunnel blocks, and **Block Exemptions**.

A network or device without settings of its own shows one line, such as "Not set for this network; Global applies.", above an empty form. A device names its network there when that network has settings of its own that are turned on. A network or device whose settings are turned off shows "Turned off; Global applies." instead, naming the same broader settings. Saving the form creates the settings, and **Remove settings for this network** or **Remove settings for this device** deletes them so the broader settings apply again. Deleting a network or device on the Clients tab deletes its settings too.

**All** lists Global and every network and device with settings of its own, with the protections that are on. Select a row to edit it.

When Sinkhole is upgraded to 1.3.0, the existing settings stay in Global and are copied into every network and device. Each copy is independent from then on. A copy is turned on only when the network's interface, or an interface of one of the device's identifiers, was selected in **Apply to**; every other copy is saved turned off, so no client is filtered that wasn't filtered before.

Global chooses its Bypass Lists like every network and device. When Sinkhole is upgraded to 1.3.1, Global's selection becomes every Bypass List that exists at that moment, so nothing changes until you edit it. A Bypass List added later is used nowhere until Global, a network, or a device selects it.

Each network or device with turned-on settings gets its own client table in the `sinkhole/bypass` anchor. A device's addresses are removed from its network's table and from Global's, and a network's subnets from Global's, so a client is blocked only by its most specific settings. Sinkhole adds no pass rules for this.

## Redirect Plain DNS \{#redirect-plain-dns}

Select **Redirect → Send port 53 to the firewall** to send ordinary TCP and UDP DNS traffic on the selected interfaces to pfSense. Sinkhole preserves the source address so network and device policy still applies.

Whenever the DNS Resolver listens on a selected interface, Sinkhole also allows direct port 53 queries addressed to that interface ahead of your interface rules. This keeps normal DHCP DNS working on isolated VLANs that block private-network destinations after you remove manual port-forward rules.

The redirect keeps its existing listener-aware targets and exemptions:

| Family | Target                                                                                     |
|--------|--------------------------------------------------------------------------------------------|
| IPv4   | `127.0.0.1` while the Resolver listens on localhost; otherwise the interface IPv4 address. |
| IPv6   | The interface IPv6 address, never `::1`.                                                   |

- **Exempt Sources** continue reaching another resolver.
- **Exempt Destinations** continue receiving DNS traffic, which supports an internal resolver on another network.

Each exemption accepts one IPv4 address, IPv6 address, CIDR network, or existing pfSense host/network alias per line. An invalid saved exemption pauses all redirect rules until it is fixed or removed. Redirected clients still need access through the Resolver's access-control settings.

The redirect rules load whenever Sinkhole is enabled on the General tab and the DNS Resolver is running. They don't depend on the Resolver's Python Module, so they keep working while pfBlockerNG or another script holds it, such as during a move from pfBlockerNG. While Redirect is on but its rules aren't loaded, a **Warning** row under **Redirect** gives the reason:

- Sinkhole is disabled.
- The DNS Resolver isn't running.
- A saved exemption is invalid.
- Sinkhole is being removed.

**Status** shows the same warning at the top of the page.

## Protect Encrypted DNS \{#protect-encrypted-dns}

The encrypted-DNS settings are independent:

- **TLS and QUIC** blocks TCP and UDP port 853 to every destination except the firewall.
- **Providers** blocks names and addresses from the selected, enabled Bypass Lists whose kind is **Encrypted DNS**.
- **Firefox** answers `use-application-dns.net` and its subdomains with `NXDOMAIN`, which turns off Firefox's automatic DNS over HTTPS selection.
- **Private Relay** answers `mask.icloud.com` and `mask-h2.icloud.com` with `NXDOMAIN`, which tells compatible Apple devices that Private Relay isn't available on this network.

Provider-list names are blocked in DNS. IPv4 addresses, IPv6 addresses, and CIDRs from the same lists are blocked on every port and protocol in the independent `sinkhole/bypass` firewall anchor. Sinkhole removes the firewall's interface addresses, gateway addresses, and DNS server addresses—including ones learned from DHCP or PPP—from those tables before loading them.

Every firewall block on the Bypass tab rejects the connection instead of dropping it, like pfSense's **Reject** action: TCP gets a reset and UDP gets an ICMP unreachable. A blocked client fails right away and falls back to the firewall's resolver instead of waiting for a timeout.

Allowed domains keep priority over provider-list name blocks. They don't override the Firefox, Private Relay, or Discovery answers because those answers are network signals rather than list blocks.

## Configure Resolver Discovery \{#configure-resolver-discovery}

Discovery controls queries for `_dns.resolver.arpa`, the Designated Resolver Discovery name defined by RFC 9462:

| Choice                                    | Answer                                                                                              |
|-------------------------------------------|-----------------------------------------------------------------------------------------------------|
| **Off**                                   | Leaves the query untouched.                                                                         |
| **Advertise the firewall's DNS over TLS** | Returns an SVCB answer with `alpn=dot`, port `853`, and the hostname from the Resolver certificate. |
| **Answer with no records**                | Returns `NOERROR` with an empty answer.                                                             |

**Advertise** requires the DNS Resolver's SSL/TLS service to be enabled with a usable certificate hostname. The Bypass page reports whether that service is on, and saving fails with a clear validation message when it isn't available.

With Sinkhole enabled and an **Apply to** interface selected, turning Discovery on adds this managed block to the DNS Resolver's **Custom options**:

```text
# Sinkhole: begin (managed by the Sinkhole package)
server:
local-zone: "_dns.resolver.arpa." transparent
# Sinkhole: end
```

Turning Discovery off or removing Sinkhole removes the zone line. The same block also carries any [Resolver Settings](/docs/configure/resolver-settings), and Sinkhole leaves every other **Custom options** line unchanged. Clients outside the selected interfaces, including the firewall itself, continue receiving `NXDOMAIN` for `_dns.resolver.arpa`.

## Protect Against Tunnels \{#protect-against-tunnels}

- **Tor → Block listed Tor relays** applies the selected, enabled Bypass Lists of kind **Tor**.
- **VPN → Block listed VPN providers** applies the selected, enabled Bypass Lists of kind **VPN**.
- **VPN → Block standard VPN ports** blocks TCP and UDP `1194`, UDP `51820`, UDP `500` and `4500`, and ESP to every destination except the firewall.

Tor and VPN list names and addresses use the same DNS and firewall behavior as encrypted-DNS provider lists. These controls reduce common alternate paths, but they don't identify every encrypted or custom tunnel.

## Exempt Devices and Servers from the Blocks \{#exempt-devices-and-servers-from-the-blocks}

**Block Exemptions** holds one **Exempt Sources** list and one **Exempt Destinations** list that every firewall block on the Bypass tab shares: **TLS and QUIC**, **Providers**, **Tor**, **Block listed VPN providers**, and **Block standard VPN ports**. Each line takes one IPv4 address, IPv6 address, CIDR network, or existing pfSense host/network alias, the same values the redirect exemptions accept. Each list holds at most 16 aliases.

- **Exempt Sources** skip the blocks. Use it for a client that must reach outside DNS servers, such as a NAS that uses DNS over TLS to `1.1.1.1`.
- **Exempt Destinations** stay reachable past the blocks from every client on the selected interfaces, such as one public resolver you trust.

An exemption never opens a path by itself. Sinkhole adds no pass rule: exempt traffic simply doesn't match the Bypass blocks and continues to your own firewall rules, which still decide whether it passes.

Exemptions cover only the firewall blocks. Provider, Tor, and VPN names from Bypass Lists stay blocked in DNS for exempt clients, so a client that finds its server by name, such as `cloudflare-dns.com`, also needs that name in **Allowed Domains**. Plain DNS on port 53 follows **Redirect** and its own exemptions instead.

If a saved block exemption becomes invalid, such as an alias that was renamed or deleted, Sinkhole keeps every block in place with no exemptions, writes one system log entry, and shows the value under **Invalid Saved Values** until it's fixed or removed.

## Manage Bypass Lists \{#manage-bypass-lists}

Bypass List sources are added, edited, enabled, and deleted on [Lists → Bypass](/docs/configure/lists#add-bypass-lists), which also has **Add from Catalog** and a **Used By** count for each list. The Bypass tab only chooses which enabled lists each context uses. An enabled Bypass List joins scheduled updates only while its matching **Providers**, **Tor**, or **VPN** protection is on.

## Verify the Active State \{#verify-the-active-state}

After saving, open **Status → Bypass** and confirm each intended protection is `On`, the selected interfaces are correct, and **Discovery Zone** is `Present` when Discovery is on. Confirm **Firewall Rules Loaded** and **Firewall Rules Current** are `Yes` for firewall protections. The Bypass Lists table shows the saved entry count and last fetch.

The plain-DNS redirect retains its existing two-observation minute reconciliation after Resolver listener changes. The `sinkhole/bypass` anchor is loaded independently of `sinkhole/ip`, so disabling either feature doesn't disturb the other.
