Define each network and device once on **Clients**, then choose what each one blocks on **Blocking**. Every client receives the policy intended for its current location.

## Why Use Networks and Devices? \{#why-use-networks-and-devices}

1. Gives each pfSense interface or VLAN its own policy while retaining Global rules for everyone.
2. Gives one device a more specific decision without requiring a separate DNS server.
3. Lets allowed domains correct false positives at the level where they matter without dropping a complete list.
4. Keeps client addresses separate from compiled lists so DHCP, neighbor, or interface changes don't reload Unbound.

## Contexts \{#contexts}

Blocking, Services, SafeSearch, Alerts, Bypass, and IP share a second row of tabs under the main tabs:

| Tab      | What the page edits                                                                                             |
|----------|-----------------------------------------------------------------------------------------------------------------|
| All      | Nothing. A read-only table lists every context that has settings of its own; select a row to open that context. |
| Global   | The settings for every client.                                                                                  |
| Networks | One network. A row of network chips picks which one.                                                            |
| Devices  | One device. A row of device chips picks which one, and the search box narrows the chips by name.                |

A banner under the row names what you are editing, such as **Editing: Network: IOT · applies to clients on IOT** or **Editing: Device: Tablet · this device only**. Each context shows only its own settings; nothing inherited from a broader context appears in its form.

The selected context follows you from tab to tab until you pick another one. A disabled network or device can still be edited, and a warning says its settings apply to no client until it is enabled again.

## Define Networks \{#define-networks}

Open **Firewall → Sinkhole → Clients**, then select **Add** below the Networks table. The editor defaults to LAN, or the first available non-WAN interface, and omits interfaces that already have a network. A client belongs to that network when its address is inside one of the interface's current IPv4 or IPv6 subnets.

Each network row has an interface and an **Enabled** checkbox. Saving returns to Clients; select the pencil or double-click a row to edit it. A device that moves between networks receives the policy for the network its current address matches.

## Define Devices \{#define-devices}

Select **Add** below the Devices table, provide a name, and add one or more identifier rows. Each row has a type and the value that applies to that type:

| Identifier type     | Addresses used for the device                                                 |
|---------------------|-------------------------------------------------------------------------------|
| IP address          | The configured IPv4 or IPv6 address.                                          |
| DHCP static mapping | Its configured address plus current addresses observed for the mapping's MAC. |
| MAC address         | Current ARP, NDP, and DHCP lease addresses for that MAC.                      |

Use **Add Identifier** and the trash buttons to maintain the rows. A device needs at least one identifier. Every address reached through any of its identifiers resolves to the same device and therefore shares one set of settings and one enabled state. Saving returns to Clients; select the pencil or double-click a row to edit it. A background job refreshes current subnets and device addresses every minute while DNS blocking has an enabled network or device, or while Bypass DNS protection needs client matching. Package Sync starts the same refresh only under that condition.

Deleting a network or device on Clients also deletes its Blocking, Services, SafeSearch, Bypass, and IP settings.

## Choose Lists and Allowed Domains \{#choose-lists-and-allowed-domains}

Open **Firewall → Sinkhole → Blocking** and pick a context:

- **Global** selects the lists that apply to every client after device and network decisions, and holds the global allowed domains.
- **Networks** selects the additional lists and allowed domains for clients on the chosen network.
- **Devices** selects the additional lists and allowed domains for the chosen device.

Each context has a **Lists** box and an **Allowed Domains** box with one domain per line. Select **Save** to apply that context. Drag the bottom corner of the **Lists** box to make it taller when you have many lists. Lists themselves are added and edited on the [Lists](/docs/configure/lists) tab.

**All** shows one row per context that has lists or allowed domains, with its list names and allowed-domain count.

## Decision Order \{#decision-order}

The most specific matching level decides each query in this exact order:

1. **Device allowed domains** — Allow immediately when the query name matches.
2. **Device lists** — Block immediately when a selected device list matches.
3. **Network allowed domains** — Allow immediately when the network exception matches.
4. **Network lists** — Block immediately when a selected network list matches.
5. **Global allowed domains** — Allow immediately when the global exception matches.
6. **Global lists** — Block when a global list matches.

The query passes when no step decides it. A client that matches no enabled network or device receives only the Global steps. A level's allowed domains override lists inherited from less-specific levels, but they don't override lists at a more-specific level that has already decided.

## Allowed-Domain Behavior \{#allowed-domain-behavior}

Each allowed-domain entry applies to the exact domain and every subdomain. For example, allowing `service.example` also allows `api.service.example` at that level.

- A device exception can pass device, network, and global lists because it is checked first.
- A network exception can pass network and global lists, but not a device-list decision.
- A global exception can pass only global lists.

## Address Conflicts \{#address-conflicts}

Several identifiers in the same device can reach the same address without creating a conflict. When two different devices claim the same current address, the first device in the Clients table wins. The Clients table and **Status → Clients** show the address under **Conflict** for every affected row so the order or identifiers can be corrected.

## Verify a Network or Device \{#verify-a-network-or-device}

1. Run `/usr/local/sbin/sinkhole --refresh-clients` or wait for the minute refresh.
2. Open **Status → Clients** and confirm the network's current subnets and the device's current addresses.
3. Query a name from a client on that network or device and compare the result with the decision order above.
4. Check for an address conflict before relying on device-specific behavior.
