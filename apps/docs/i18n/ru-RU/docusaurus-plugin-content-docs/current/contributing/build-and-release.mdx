Собирайте, тестируйте и выпускайте Sinkhole через корневую рабочую область Nova, чтобы пакет и документация проходили один и тот же проверенный процесс.

## Предварительные требования \{#prerequisites}

- Используйте диапазон версий Node.js из корневого `package.json` и версию npm, выбранную в его поле `packageManager`.
- Для окончательной сборки `.pkg` используйте FreeBSD с рабочей копией дерева портов pfSense.
- Для проверки установки, обновления, блокировки и удаления используйте одноразовый лабораторный стенд pfSense.

Перед сборкой пакета задайте в `PFSENSE_PORTS_DIR` путь к рабочей копии дерева портов FreeBSD для pfSense. Рабочая копия должна содержать `Mk/bsd.port.mk`, а место назначения `sysutils/pfSense-pkg-Sinkhole` должно быть свободно для временной копии сборки.

## Установка зависимостей \{#install-dependencies}

Из корня репозитория:

```sh
npm install
```

Nova считывает рабочие области из `nova.config.json`. Запускайте команды рабочих областей из корня, кроме случаев, когда намеренно диагностируете команду отдельного пакета.

## Проверка каждого изменения \{#check-every-change}

```sh
npm run check
npm run build
```

`npm run check` выполняет линтинг, проверку типов и тесты корневой рабочей области, пакета и документации. `npm run build` подготавливает порт pfSense и создает производственную сборку документации в каталоге `build/`.

Если на компьютере нет пригодной среды выполнения PHP, команда `SINKHOLE_SKIP_PHP_TESTS=1 npm run check` запускает все доступные проверки, но не заменяет обязательные тесты пакета перед выпуском. Изменения пакета также требуют автономных тестов PHP и Python, тестов восстановления и межъязыковых тестов, описанных в правилах репозитория.

## Сборка пакета выпуска \{#build-the-release-package}

После `npm run build` запустите окончательную команду упаковки во FreeBSD:

```sh
npm run deploy
```

Сценарий развертывания запускает `make package` в настроенной рабочей копии дерева портов, заново создает манифест с признаком vital и `FreeBSD:*`, проверяет оба свойства и записывает версионированные и стабильные файлы `.pkg`, а также файлы SHA-256 в `packages/sinkhole/build/release/`.

Команда намеренно завершается ошибкой не во FreeBSD или без `PFSENSE_PORTS_DIR`. Никогда не используйте вместо артефакта выпуска пакет, собранный в другой операционной системе.

## Запись изменения \{#record-the-change}

По мере внесения изменений используйте процесс ведения журнала изменений Nova:

```sh
npm run changelog
```

Выберите затронутую рабочую область и категорию примечания к выпуску, соответствующую видимому пользователю изменению. Для каждого изменения оставляйте одну связную запись и соблюдайте принятый в репозитории повелительный стиль настоящего времени.

## Подготовка выпуска \{#cut-a-release}

1. Выполните `npm run check` и `npm run build` для чистого кандидата на выпуск.
2. Запустите `nova utility changelog --release`, чтобы выбрать версию, обновить версии пакетов и записать журналы изменений.
3. Выполните `npm run deploy` на настроенной системе сборки FreeBSD.
4. Установите и обновите артефакт, проверьте блокировку и удалите его на одноразовом лабораторном стенде pfSense.
5. Опубликуйте выпуск GitHub с версионированным и стабильным пакетами и артефактами контрольных сумм.

Публикация выпуска запускает рабочий процесс артефакта пакета и рабочий процесс развертывания документации. Выпуск pfSense не указывается как поддерживаемый, пока не пройдет полная лабораторная проверка.

## Изменения документации \{#documentation-changes}

Используйте явные английские идентификаторы заголовков, например `{#build-and-release}`, чтобы переведенные страницы сохраняли стабильные якорные ссылки. Форматируйте таблицы Markdown командой `npx nova recipe misc fix-markdown-tables`, затем запускайте те же корневые команды проверки и сборки.

Английские страницы служат источником для всех 17 переведенных локализаций. Не переводите названия продуктов, точно сохраняйте код, пути и английские якорные ссылки и не обещайте функции, которые еще не реализованы.
