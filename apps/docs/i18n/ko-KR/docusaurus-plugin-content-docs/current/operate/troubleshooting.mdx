Status 패널과 시스템 로그에서 문제를 일으킨 특정 목록, 범위, 규칙, 리스너, 잠금 또는 런타임 상태까지 추적합니다.

## 확인할 위치 \{#where-to-look}

- **Firewall → Sinkhole → Status**에는 목록, 카탈로그, 클라이언트 맵, 알림, Bypass, IP, 컴파일, 배포 및 Resolver 상태가 표시됩니다.
- **Status → System Logs → System → General**에는 `Sinkhole:`로 시작하는 운영 로그 줄이 표시됩니다.
- `/usr/local/sbin/sinkhole --help`는 지원되는 유지 관리 모드를 출력합니다.

구성을 변경하기 전에 Status 값과 관련 로그 줄을 보관하는 것이 좋습니다. 전체 `config.xml` 출력에는 비밀 값이 포함될 수 있으므로 보고서에 첨부하지 않습니다.

## Sinkhole이 비활성 상태임 \{#sinkhole-is-inactive}

**Summary → Sinkhole** 뒤에 표시되는 이유를 확인합니다.

- **Sinkhole is disabled** — Resolver와 Python 슬롯이 준비되면 **General → Enable**을 선택합니다.
- **DNS Resolver is disabled** — Sinkhole을 저장하기 전에 Resolver를 활성화하고 적용합니다.
- **Python script slot is owned** — 충돌하는 DNSBL/Python 통합을 비활성화하거나 Sinkhole을 비활성 상태로 둡니다. Sinkhole은 다른 통합을 대체하지 않습니다.
- **Python mode or position changed** — Sinkhole이 슬롯을 소유하는 동안 Sync가 Python 모드와 `pre_validator`를 복원할 수 있도록 Sinkhole General 설정을 다시 저장합니다.
- **Runtime files unavailable** — General 설정을 저장하여 패키지 Sync를 실행하거나 재부팅하여 pfSense 패키지 Sync가 RAM 디스크 파일을 복원하도록 합니다.

`/var`를 메모리에 두는 시스템에서는 부팅할 때마다 패키지 Sync가 누락된 런타임 파일을 복원하고 패키지가 시작된 후 필요하면 Unbound를 재시작합니다. 따라서 부팅 직후 누락된 초기 런타임은 패키지 시작 과정에서 복구되어야 합니다.

부팅 복원이 실패하면 **Status → System Logs → System → General**에 `sinkhole` 태그로 기록되며 Sinkhole 알림도 생성됩니다.

## 도메인이 차단되지 않음 \{#a-domain-is-not-blocked}

1. 목록이 활성화되어 있고 저장된 항목이 있으며 오류 후 마지막 정상 사본을 대체하지 않았는지 확인합니다.
2. 클라이언트의 현재 장치와 네트워크에 대한 [판단 순서](/docs/configure/scopes#decision-order)를 따릅니다.
3. **Compile Needed**와 **Deployment Needed**가 `No`인지 확인한 다음 컴파일, 배포 및 로드된 세대를 비교합니다.
4. 클라이언트가 pfSense에 직접 또는 **Bypass → Redirect**를 통해 쿼리하는지 확인합니다.

Unbound는 Python 모듈보다 먼저 기본 제공 영역 `test.`, `invalid.`, `onion.`, `localhost.`에 응답합니다. 이러한 영역 중 하나에서 실제 테스트를 실행하면 Sinkhole을 거치지 않습니다.

배포 시 이름이 추가되거나 하위 트리 범위가 넓어지면 `flush_zone`은 캐시 항목을 만료된 것으로만 표시하므로 Sinkhole이 새 세대가 로드된 후 Unbound를 다시 로드합니다. **Serve Expired**가 켜져 있으면 Unbound 1.18이 해당 항목을 계속 제공할 수 있지만 `unbound-control reload`는 메시지 및 RRset 캐시를 지웁니다.

## CNAME 결과가 불완전해 보임 \{#a-cname-result-looks-incomplete}

원래 이름이 목록에 없어도 CNAME 대상이 목록에 있으면 쿼리가 차단됩니다. 목록에 있는 대상에 AAAA와 같은 요청 레코드 유형이 없으면 주소 없이 CNAME만 응답에 남을 수 있습니다.

허용된 쿼리 이름은 계속 허용됩니다. 따라서 덜 구체적인 CNAME 대상이 쿼리 이름에 대한 명시적인 허용 도메인 판단을 재정의하지 않습니다.

## 장치에 잘못된 정책이 적용됨 \{#a-device-gets-the-wrong-policy}

- `/usr/local/sbin/sinkhole --refresh-clients`를 실행하고 **Status → Scopes**를 확인합니다.
- 네트워크 행에 인터페이스의 현재 서브넷이 표시되고 장치 행에 현재 주소가 표시되는지 확인합니다.
- 공유 주소는 표에서 첫 번째 장치가 우선하므로 모든 **Conflict** 값을 해결합니다.
- 정적 매핑의 경우 구성된 주소와 해당 MAC에서 관찰된 현재 주소를 모두 확인합니다.

ISC 임대 종료 시간은 인터페이스의 임대 시간 설정에 따라 GMT 또는 방화벽 로컬 시간일 수 있으며, Kea 임대 시간은 이미 로컬 시간입니다. Sinkhole은 임대가 현재 유효한지 판단할 때 이러한 pfSense 의미 체계를 따릅니다.

## 목록 또는 카탈로그 업데이트 실패 \{#list-or-catalog-update-failed}

DNS, Bypass 또는 IP 다운로드, 구문 분석, 유효성 검사에 실패하면 이전 저장 사본을 유지하고 오류를 기록합니다. DNS는 실패한 출처를 기다리지 않고 배포된 로컬 세대에서 계속 작동합니다.

카탈로그는 검색을 열거나 새로 고칠 때만 가져오며 가져오기에 실패하면 캐시된 마지막 정상 카탈로그를 유지합니다. 다시 강제로 새로 고치기 전에 HTTPS 연결, 출처 URL 및 Status 오류를 확인합니다.

## 일반 DNS 리디렉션이 일시 중지되거나 누락됨 \{#plain-dns-redirect-is-paused-or-missing}

- **Paused** — Bypass 패널에 표시된 잘못된 예외를 모두 수정하거나 제거합니다.
- **No family address** — 인터페이스에 해당 패밀리를 추가하거나 그 패밀리의 규칙을 생성할 수 없음을 수용합니다.
- **Resolver does not listen** — **DNS Resolver → Network Interfaces**를 변경하거나 해당 리디렉션 선택을 제거합니다.
- **Rules missing or out of date** — 두 번의 분 단위 관찰을 기다린 다음 **Last parse error**와 시스템 로그를 확인합니다.
- **Queries are refused** — Resolver의 액세스 제어 구성에 클라이언트 네트워크를 추가합니다.

pfSense 패키지 잠금이 유지되는 동안 또는 pfSense가 변경되지 않은 규칙 텍스트를 이미 거부한 경우 분 단위 검사는 필터를 다시 로드하지 않습니다. 잘못된 구성을 변경하면 다음 두 번의 관찰에서 조정됩니다.

측정된 FreeBSD 동작은 비루프백 인터페이스에서 `::1`로 다시 쓴 트래픽을 삭제하므로 IPv6 리디렉션 대상은 항상 인터페이스 주소를 사용합니다. 측정한 FreeBSD 14와 16은 패밀리 한정자가 없는 혼합 목록에서 첫 번째 패밀리만 유지했으므로 혼합 패밀리 예외를 별도의 `inet` 및 `inet6` 규칙으로 생성합니다.

## IP 차단이 설정과 일치하지 않음 \{#ip-blocking-does-not-match-settings}

1. **IP and Country Blocking → State**가 `On`이고 의도한 인터페이스와 방향이 나열되는지 확인합니다.
2. 최종 패밀리 테이블 수, 건너뛴 줄, 마지막 업데이트 및 마지막 오류를 확인합니다.
3. **IP Anchor**가 `Yes`인지 확인합니다. `Out of Date`는 로드된 앵커가 현재 파일이나 설정과 일치하지 않음을 의미합니다.
4. 허용 목록을 검토하고 방화벽, 게이트웨이 및 DNS 주소가 자동으로 제거된다는 점을 기억합니다.

`sinkhole/ip` 앵커는 일반적인 pfSense 필터 다시 로드 후에도 유지되며 초기 패키지 규칙 훅을 통해 pass-quick 규칙보다 앞에 위치합니다. 분 단위 검사는 비어 있거나 변경된 앵커를 직접 다시 로드하며 기능을 끄면 앵커를 비웁니다.

## 알림이 도착하지 않음 \{#alerts-do-not-arrive}

- 규칙이 활성화되어 있고 목록 선택과 클라이언트 선택이 모두 차단 응답과 일치하는지 확인합니다.
- 이벤트를 규칙의 반복 간격 및 실행당 20개, 규칙당 시간당 60개, 미확인 알림 50개 한도와 비교합니다.
- **Status → Alerts**에서 만료, 보류, 삭제 또는 오류 수를 확인합니다.
- pfSense에 구성된 원격 서비스를 **System → Advanced → Notifications**에서 별도로 테스트합니다.

10분이 지난 이벤트는 만료되며 실행은 40초의 시간 예산이 지나면 전송을 중단하여 남은 작업을 다음 분에 계속할 수 있게 합니다. WebGUI 알림 문구는 `file_notice()`를 통해 pfSense 시스템 로그에도 나타납니다.

## 메모리 사용량이 높음 \{#memory-use-is-high}

이름 300,000개를 사용한 측정 테스트에서 Unbound RSS는 41 MiB에서 103 MiB로 증가했고 최대 정책 메모리는 이름당 약 157바이트였습니다. 실제 사용량은 고유하게 정규화된 이름, 범위 할당 및 실행 중인 Resolver에 따라 달라집니다.

대규모 출처를 추가하기 전후에 Status 항목 수와 Unbound 메모리를 비교하는 것이 좋습니다. 사용하지 않는 목록을 비활성화하면 다음 컴파일 시 활성 정책에서 제외됩니다.

## 문제 보고 \{#report-a-problem}

Sinkhole 버전, pfSense 에디션과 릴리스, FreeBSD 릴리스, 정확한 Status 상태, 재현 단계 및 민감 정보를 제거한 `Sinkhole:` 로그 줄을 포함하여 [GitHub 이슈](https://github.com/mrjackyliang/pfsense-sinkhole/issues)를 엽니다. MaxMind 자격 증명, 전체 구성 파일, 목록 내용 또는 비공개 클라이언트/도메인 데이터는 포함하지 않습니다.
