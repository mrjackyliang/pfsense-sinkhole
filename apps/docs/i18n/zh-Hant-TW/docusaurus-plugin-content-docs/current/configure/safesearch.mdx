使用 **Firewall → Sinkhole → SafeSearch** 讓某個網路或設備上的搜尋引擎維持安全模式，無需變更任何瀏覽器或設備設定。

## 為什麼使用 SafeSearch？ \{#why-use-safesearch}

1. 在網路層級鎖定安全模式，因此未登入的瀏覽器、新設備或私密視窗仍會取得過濾後的結果。
2. 涵蓋所有 Google 國家/地區網域，而不只是 `google.com`，因此改用 `google.co.uk` 也無法繞過。
3. 與封鎖清單使用相同的作用域，因此可以只為兒童 VLAN 啟用 SafeSearch，而網路的其他部分不受影響。

## 選擇作用域和搜尋引擎 \{#choose-a-scope-and-engines}

1. 在 **Scope** 中選擇 **Global**、一個已設定的網路或一個已設定的設備。
2. 勾選要鎖定的每個搜尋引擎，並為 YouTube 選擇 **Moderate** 或 **Strict**。
3. 選擇 **Save**。

網路或設備必須先存在於 **Scopes** 中，才會出現在這裡。儲存時會立即查詢每個安全主機，並在背景套用變更。

## 作用域如何合併 \{#how-scopes-combine}

用戶端會取得為 **Global**、其所在網路和其設備所選的全部搜尋引擎的合集。當 YouTube 同時出現兩個等級時，以 **Strict** 為準。

SafeSearch 在封鎖之後套用。清單或已封鎖的服務為該用戶端封鎖的名稱仍維持封鎖，允許網域也不會關閉 SafeSearch。與任何沒有作用域的用戶端一樣，防火牆本身的查詢會取得為 **Global** 所選的搜尋引擎。

## 回應如何運作 \{#how-the-answer-works}

對於已選擇的搜尋引擎，Sinkhole 會將該引擎的名稱回應為指向安全主機的 CNAME，並附上安全主機的地址，與手寫的 Unbound 檢視所給出的回應相同。其他記錄類型（例如 HTTPS 記錄）只會收到 CNAME，因此瀏覽器無法利用提示繞過安全主機。

Sinkhole 會在儲存時以及每次清單更新時查詢每個安全主機的地址，查詢失敗時保留最後一次有效的地址。如果某個搜尋引擎的安全主機從未傳回過地址，該引擎會在其作用域內遭到封鎖，直到查詢成功。

SafeSearch 回應永遠不會存入 Resolver 的快取，因此一個用戶端的回應絕不會傳給作用域以外的用戶端。

## 驗證 SafeSearch \{#verify-safesearch}

1. 開啟 **Status**，確認 **SafeSearch** 面板列出每個安全主機及其地址，且沒有錯誤。
2. 在作用域內的用戶端上查詢一個搜尋引擎名稱，例如 `nslookup www.google.com`，並確認回應指向安全主機。
3. 在作用域外的用戶端上，確認同樣的查詢傳回該引擎的正常回應。

用戶端送往其他地方的加密 DNS 會跳過所有 DNS 原則，包括 SafeSearch。[防止繞過](/docs/configure/bypass-protection)可讓所選介面維持在 Sinkhole 的 DNS 路徑上。
