使用 **Firewall → Sinkhole → SafeSearch** 让某个网络或设备上的搜索引擎保持安全模式，无需更改任何浏览器或设备设置。

## 为什么使用 SafeSearch？ \{#why-use-safesearch}

1. 在网络层面锁定安全模式，因此未登录的浏览器、新设备或隐私窗口仍会得到过滤后的结果。
2. 涵盖所有 Google 国家/地区域名，而不只是 `google.com`，因此切换到 `google.co.uk` 也无法绕过。
3. 与阻止列表使用相同的 Global、网络和设备上下文，因此可以只为儿童 VLAN 启用 SafeSearch，而网络的其他部分不受影响。

## 选择上下文和搜索引擎 \{#choose-a-context-and-engines}

1. 在主选项卡下方的[上下文行](/docs/configure/scopes#contexts)中选择 **Global**、一个网络或一台设备。
2. 勾选要锁定的每个搜索引擎，并为 YouTube 选择 **Moderate** 或 **Strict**。
3. 选择 **Save**。

网络或设备必须先在 **Clients** 中存在，才会出现在上下文行中。保存时会立即查找每个安全主机，并在后台应用更改。**All** 列出每个至少锁定一个搜索引擎的上下文；选择某行即可编辑该上下文。

| Brave Search | `search.brave.com`                                                   | `forcesafe.search.brave.com`                                             |
| Startpage    | `startpage.com`、`www.startpage.com`                                  | `safe.startpage.com`                                                     |

## 上下文如何合并 \{#how-contexts-combine}

客户端会获得为 **Global**、其所在网络和其设备所选的全部搜索引擎的合集。当 YouTube 同时出现两个级别时，以 **Strict** 为准。

SafeSearch 在阻止之后应用。列表或已阻止的服务为该客户端阻止的名称仍保持阻止，允许域名也不会关闭 SafeSearch。与任何不属于任何网络或设备的客户端一样，防火墙自身的查询会获得为 **Global** 所选的搜索引擎。

## 应答如何工作 \{#how-the-answer-works}

对于已选择的搜索引擎，Sinkhole 会将该引擎的名称应答为指向安全主机的 CNAME，并附上安全主机的地址，与手写的 Unbound 视图给出的应答相同。其他记录类型（例如 HTTPS 记录）只会收到 CNAME，因此浏览器无法利用提示绕过安全主机。

Sinkhole 会在保存时以及每次列表更新时查找每个安全主机的地址，查找失败时保留最后一次有效的地址。如果某个搜索引擎的安全主机从未返回过地址，该引擎会在其上下文内被阻止，直到查找成功。

SafeSearch 应答永远不会存入 Resolver 的缓存，因此一个客户端的应答绝不会传给该上下文之外的客户端。

## 验证 SafeSearch \{#verify-safesearch}

1. 打开 **Status**，确认 **SafeSearch** 面板列出了每个安全主机及其地址，且没有错误。
2. 在该上下文内的客户端上查询一个搜索引擎名称，例如 `nslookup www.google.com`，并确认应答指向安全主机。
3. 在该上下文外的客户端上，确认同样的查询返回该引擎的正常应答。

客户端发往其他地方的加密 DNS 会跳过所有 DNS 策略，包括 SafeSearch。[防绕过保护](/docs/configure/bypass-protection)可让所选接口保持在 Sinkhole 的 DNS 路径上。
