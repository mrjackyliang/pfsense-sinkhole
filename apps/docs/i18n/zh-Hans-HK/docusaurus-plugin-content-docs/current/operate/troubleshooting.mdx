从 Status 面板和系统日志追踪问题，定位导致问题的具体列表、作用域、规则、监听地址、锁或运行时状态。

## 查看位置 \{#where-to-look}

- **Firewall → Sinkhole → Status** 显示列表、目录、客户端映射、警报、Bypass、IP、编译、部署和 Resolver 状态。
- **Status → System Logs → System → General** 显示以 `Sinkhole:` 开头的运行日志行。
- `/usr/local/sbin/sinkhole --help` 输出支持的维护模式。

建议在更改配置之前保留 Status 值和相关日志行。完整的 `config.xml` 输出可能包含机密信息，不应附加到报告中。

## Sinkhole 处于非活动状态 \{#sinkhole-is-inactive}

根据 **Summary → Sinkhole** 后面的原因处理：

- **Sinkhole is disabled** — 在 Resolver 和 Python 插槽准备就绪后选择 **General → Enable**。
- **DNS Resolver is disabled** — 在保存 Sinkhole 之前启用并应用 Resolver。
- **Python script slot is owned** — 禁用冲突的 DNSBL/Python 集成，或让 Sinkhole 保持禁用；Sinkhole 不会替换它。
- **Python mode or position changed** — 再次保存 Sinkhole 的 General 设置，以便 Sync 在 Sinkhole 拥有插槽时恢复 Python 模式和 `pre_validator`。
- **Runtime files unavailable** — 通过保存 General 设置运行软件包 Sync，或重新启动并让 pfSense 的软件包 Sync 恢复 RAM 磁盘文件。

在 `/var` 位于内存中的系统上，每次启动时的软件包 Sync 会恢复缺失的运行时文件，并在软件包启动后按需重启 Unbound。因此，启动后立即缺失的早期运行时文件应在软件包启动期间自动恢复。

啟動還原失敗時，會以 `sinkhole` 標記記錄在 **Status → System Logs → System → General** 中，並同時產生 Sinkhole 通知。

## 某个域名未被阻止 \{#a-domain-is-not-blocked}

1. 确认列表已启用且具有已保存条目，并且错误没有替换其最后有效副本。
2. 按客户端当前设备和网络遵循[决策顺序](/docs/configure/scopes#decision-order)。
3. 确认 **Compile Needed** 和 **Deployment Needed** 均为 `No`，然后比较编译、部署和加载代次。
4. 确认客户端直接查询 pfSense，或通过 **Bypass → Redirect** 查询。

Unbound 会先于 Python 模块应答内置的 `test.`、`invalid.`、`onion.` 和 `localhost.` 区域。在这些区域下进行实时测试不会执行 Sinkhole。

当部署增加名称或扩大子树时，Sinkhole 会在新代次加载后重新加载 Unbound，因为 `flush_zone` 只会把缓存条目标记为过期。启用 **Serve Expired** 时，Unbound 1.18 仍可能提供这些条目，而 `unbound-control reload` 会清除消息和 RRset 缓存。

## CNAME 结果看起来不完整 \{#a-cname-result-looks-incomplete}

如果查询的 CNAME 目标已列入列表，即使原始名称未列入列表，该查询也会被阻止。如果列入列表的目标没有所请求类型的记录（例如 AAAA），应答可以保留 CNAME 但不包含地址。

明确允许的查询名称仍会保持允许。这样可防止不太具体的 CNAME 目标覆盖对所查询名称的显式允许域名决定。

## 设备获得了错误策略 \{#a-device-gets-the-wrong-policy}

- 运行 `/usr/local/sbin/sinkhole --refresh-clients` 并检查 **Status → Scopes**。
- 确认网络行显示接口的当前子网，设备行显示其当前地址。
- 解决所有 **Conflict** 值，因为按表格顺序出现的第一个设备会赢得共享地址。
- 对于静态映射，请同时检查其配置地址以及为其 MAC 观察到的当前地址。

ISC 租约时间可能采用 GMT 或防火墙本地时间，具体取决于接口的租约时间设置；Kea 租约时间已经是本地时间。Sinkhole 在判断租约是否为当前租约时遵循这些 pfSense 语义。

## 列表或目录更新失败 \{#list-or-catalog-update-failed}

DNS、Bypass 或 IP 下载、解析或验证失败时会保留之前的已保存副本并记录错误。DNS 继续使用已部署的本地代次，而不会等待失败的来源。

目录只在搜索打开或刷新时获取；获取失败会保留缓存的最后有效目录。强制再次刷新前，请确认 HTTPS 连接、来源 URL 和 Status 错误。

## 普通 DNS 重定向已暂停或缺失 \{#plain-dns-redirect-is-paused-or-missing}

- **Paused** — 修复或删除 Bypass 面板中显示的每个无效豁免。
- **No family address** — 为接口添加该地址族，或接受无法为其生成规则。
- **Resolver does not listen** — 更改 **DNS Resolver → Network Interfaces**，或移除该重定向选择。
- **Rules missing or out of date** — 等待两次每分钟观察，然后检查 **Last parse error** 和系统日志。
- **Queries are refused** — 将客户端网络添加到 Resolver 的访问控制配置。

当 pfSense 的软件包锁被持有，或 pfSense 已拒绝未改变的规则文本时，每分钟检查不会重新加载过滤器。更正无效配置后，接下来的两次观察会进行协调。

IPv6 重定向目标始终使用接口地址，因为实测 FreeBSD 会丢弃从非回环接口重写到 `::1` 的流量。混合地址族豁免会分别生成 `inet` 和 `inet6` 规则，因为实测 FreeBSD 14 和 16 在不限定地址族的混合列表中只保留第一个地址族。

## IP 阻止与设置不符 \{#ip-blocking-does-not-match-settings}

1. 确认 **IP and Country Blocking → State** 为 `On`，并列出了预期接口和方向。
2. 检查最终地址族表计数、跳过行数、上次更新和上次错误。
3. 确认 **IP Anchor** 为 `Yes`；`Out of date` 表示已加载锚点与当前文件或设置不匹配。
4. 检查允许列表，并记住系统会自动移除防火墙、网关和 DNS 地址。

`sinkhole/ip` 锚点可在普通 pfSense 过滤器重新加载后继续存在，并通过早期软件包规则挂钩位于 pass-quick 规则之前。每分钟检查会直接重新加载空白或发生变化的锚点，而关闭该功能会清空锚点。

## 未收到警报 \{#alerts-do-not-arrive}

- 确认规则已启用，并且其列表选择和客户端选择都与被阻止应答匹配。
- 将事件与规则的重复时间窗口、每次运行 20 条、每条规则每小时 60 条和 50 条未读通知上限进行比较。
- 检查 **Status → Alerts** 是否有过期、受抑制、已丢弃或错误计数。
- 在 **System → Advanced → Notifications** 下单独测试 pfSense 配置的远程服务。

超过 10 分钟的事件视为过期；一次运行达到 40 秒预算后会停止发送，以便剩余工作在下一分钟继续。WebGUI 通知文本也会通过 `file_notice()` 出现在 pfSense 系统日志中。

## 内存使用量很高 \{#memory-use-is-high}

对 300,000 个名称的实测使 Unbound RSS 从 41 MiB 增至 103 MiB，策略内存峰值约为每个名称 157 字节。实际用量取决于唯一规范化名称、作用域分配和正在运行的 Resolver。

建议在添加大型来源前后，将 Status 条目计数与 Unbound 内存进行比较。禁用未使用的列表后，它会在下一次编译时退出活动策略。

## 报告问题 \{#report-a-problem}

请创建 [GitHub issue](https://github.com/mrjackyliang/pfsense-sinkhole/issues)，并附上 Sinkhole 版本、pfSense 版本和版本号、FreeBSD 版本、准确的 Status 状态、复现步骤以及经过清理的 `Sinkhole:` 日志行。不要包含 MaxMind 凭据、完整配置文件、列表内容或私有客户端/域名数据。
