# PROJECT_RULES.md

## Project Identity

### Name and Description

- **Project name:** Sinkhole for pfSense (`pfsense-sinkhole`)
- **Description:** Sinkhole blocks unwanted websites on your pfSense network, with separate
  block lists for each network or device.
- **Primary languages:** PHP for the package on pfSense, TypeScript and JavaScript for Nova
  tooling, tests and the docs site, and shell for the package build script.
- **Frameworks / runtimes:** The pfSense package system (a FreeBSD port), Nova's monorepo
  tooling on Node.js, and Docusaurus with Nova's preset for the docs.

### Repository URL

- **URL:** https://github.com/mrjackyliang/pfsense-sinkhole

### Source Structure

- **`packages/sinkhole/port/`** — The FreeBSD port:
  - `Makefile.template` is the port recipe. `%%NOVA_PORTVERSION%%` is stamped from the
    workspace version when the port is staged.
  - `pkg-descr` and `pkg-plist` hold the package description and the installed-file list.
  - `files/pkg-install.in` and `files/pkg-deinstall.in` are the package lifecycle hooks.
  - `files/usr/local/pkg/sinkhole.xml` defines the WebGUI menu, settings, lifecycle callbacks,
    package filter-rule hook and pre-form localization callback.
  - `files/usr/local/pkg/sinkhole.inc` reads the settings and keeps the pfSense-managed
    cron entries and DNS Resolver integration in sync.
  - `files/usr/local/pkg/priv/sinkhole.priv.inc` grants the General, Lists, list editor,
    Services, Scopes, scope editor, Alerts, alert editor, Bypass, Bypass-list editor, IP,
    IP-list editor, Status and About WebGUI privileges at run time.
  - `files/usr/local/pkg/sinkhole/` contains the domain, Bypass and IP parsers, list, scope,
    alert-rule, DNS redirect, Bypass and IP rule configuration, Bypass last-good storage and
    updater, GeoLite2 importer, popular-list
    catalog parser, cache and card-presentation boundary, blocked-service registry parser,
    per-scope configuration, cache and data-URI presentation boundary,
    saved-list store, compiler, alert processor, client-map builder and source boundary,
    compiled/deployed digest, client-map, alert and catalog status, owed cache-clear and removal
    lifecycle state, update/runtime/client/alert locking, platform adapter, GitHub release-update
    manager and persistent check/status state, tested pfSense release registry, package translator,
    English source catalog, the byte-preserving managed Unbound Custom-options transformer,
    keyed validation exceptions, Unbound watcher and query-response module source, and the fixed
    RAM-disk restore script.
  - `files/usr/local/www/sinkhole-lists.php`, `sinkhole-scopes.php`, `sinkhole-alerts.php`,
    `sinkhole-bypass.php` and `sinkhole-ip.php` are pfSense-style list pages with sortable tables, row actions,
    Add navigation and page-wide settings where applicable. Their matching
    `sinkhole-lists_edit.php`, `sinkhole-scopes_edit.php`, `sinkhole-alerts_edit.php`,
    `sinkhole-bypass_edit.php` and `sinkhole-ip_edit.php` pages own add, edit and invalid-row
    repair forms. `sinkhole-services.php`, `sinkhole-status.php` and `sinkhole-about.php` are
    the single-page blocked-service, operational-status and package-information views.
  - `files/usr/local/sbin/sinkhole` runs scheduled/manual full updates and selective
    background applies under the update lock, including refreshed pending-apply loops, durable
    cache-clear handoffs, post-run client refreshes and per-run failure reporting. Its
    `--refresh-clients` mode rebuilds only local interface, neighbor, lease and static-mapping
    state under an independent nonblocking lock. Its `--alerts` mode rotates and validates
    block events, enforces repeat windows and calls the selected pfSense notification channels
    under a separate nonblocking lock. Its `--check-updates` and `--self-update` modes check the
    latest GitHub release and perform the verified detached package replacement.
  - `files/usr/local/share/pfSense-pkg-Sinkhole/info.xml` is the package manifest, and
    `logo.svg` is a byte copy of the documentation logo for the About page.
    `release-signing.pub` is the installed release trust list; the repository copy intentionally
    contains comments only.
- **`packages/sinkhole/scripts/`** — `check-package.mjs` validates the port structure, release
  trust-list syntax and packaging, and compares the installed and documentation logo bytes,
  `stage-package.mjs` copies the port to `build/port` and stamps the version, and
  `build-package.sh` runs `make package` in a pfSense ports checkout, rebuilds the artifact
  as a vital `FreeBSD:*` package and writes versioned and stable release copies.
  `test-domain.sh`,
  `test-python.sh`, `test-restore-runtime.sh` and `test-e2e.sh` run the package's offline
  PHP, Python, boot-restore and cross-language suites.
- **`packages/sinkhole/tests/`** — Domain/Bypass/IP parser, GeoLite2, popular-list catalog fixture,
  card grouping/filtering, blocked-service registry/cache/storage/compilation, cache fallback,
  search/add, scoped compiler, alert-manifest, DNS redirect, Bypass and IP filter-rule
  tests, client-map fixtures,
  deployment digest, durable cache clear, refreshed lock handoff, removal-marker lifecycle,
  download policy, last-good storage, pfSense adapter, alert delivery, status and embedded Unbound
  callback/watcher/event tests with local pfSense and Unbound stubs, GitHub update scheduling,
  notice, asset, digest, signature, lock, CLI and About-bar tests, plus the PHP-to-Python scoped
  alert end-to-end fixtures.
- **`apps/docs/`** — `docusaurus.config.ts`, `sidebars.ts`, the pages in `docs/`, the home
  page in `src/pages/`, the docs tests in `src/tests/`, and the icons, web manifest and
  thumbnails in `static/`.
- **`tests/`** — Root Vitest suites for the project contract and dotenv files.

The package implements global, VLAN-network and device block-list and blocked-service scopes, rule-scoped WebGUI
and remote alerts, optional interface-scoped Bypass protection including plain-DNS redirect,
encrypted-DNS signals and provider/tunnel controls, on-demand popular-list catalog search, and
separate interface/direction-scoped IP-list and MaxMind country blocking.

Run these from the repository root. Nova runs each workspace's scripts from the workspaces
in `nova.config.json`.

## Architecture and Data

### Architecture

- **Today** — Nova's starter. `sinkhole.xml` defines a settings page, `sinkhole.inc` reads
  the settings and installs a cron entry with pfSense's `install_cron_job()`, and
  `sbin/sinkhole` runs from cron and writes a message to the system log.
- **Boundaries for the real package** — Keep the WebGUI, list downloads and storage, the DNS
  Resolver integration, alerts, the DNS redirect, and IP and country blocking behind
  separate boundaries, with the WebGUI only validating and saving settings.

### Data Flow and Ownership

- **Settings** — pfSense owns the configuration, under `installedpackages/sinkhole`.
- **Lists** — Downloaded, validated, then saved on the firewall in package-owned storage. DNS
  uses only saved copies, and a failed download keeps the previous copy.
- **Alerts** — Leave the firewall only through the pfSense notifications the administrator
  set up.

### Error Strategy

- A failed download, parse or alert never interrupts DNS and never removes working lists.
- Failures go to the system log and to the package's status in the WebGUI.
- Settings are validated when saved and again when used.

## Project Guardrails

### Security, Privacy, and Secrets

- No secrets in the repository. `.env` files are ignored by git.
- Treat downloaded list contents as untrusted input.
- Block events reveal what people try to visit. Keep them on the firewall apart from the
  configured pfSense notifications, and never log the full `config.xml`.
- Escape everything the WebGUI renders, and never build shell commands from settings or list
  contents.

### Platform and Domain Rules

#### Off by Default

Everything is off by default. On a fresh install, the network behaves exactly as if Sinkhole
were not there:
- no DNS Resolver Python script taken
- no lists, services or scopes
- no redirect, IP or bypass rules
- no blocked answers
- no client-map refresh job or client-map files

Nothing is blocked or redirected until an administrator assigns it. Every new setting that
blocks, redirects or changes an answer must default to off, and upgrades must never turn one
on.

#### pfSense Package Lifecycle

- Install and remove through pfSense package conventions, with files only where the port's
  layout puts them.
- Read and write settings through pfSense's configuration APIs, never by editing
  `config.xml` as text.
- Install and upgrade hooks are repeatable and keep user settings and saved lists.
- Removal stops schedules, restores the DNS Resolver and removes the files in
  `/var/unbound`, plus Sinkhole's lock and status files under `/var/run`. Saved lists and
  settings stay unless Keep Settings is off, as in pfBlockerNG, because pkg can run an
  upgrade as a removal followed by an install.
- Saved lists survive DNS Resolver restarts and pfSense upgrades.
- pfSense re-runs every package's sync at boot and on every WAN address change
  (`rc.start_packages`), so a sync that has nothing to change writes no configuration
  revision, compiles nothing and leaves Unbound alone.

#### DNS Blocking Rules

- DNS never waits for a list download. The Unbound module loads only local files when
  Unbound starts, and a failed download keeps the previous saved copy.
- Sinkhole runs as an Unbound Python module, installed as `/var/unbound/sinkhole.py` through
  the DNS Resolver's Python settings (`unbound/python`, `python_order`, `python_script`).
  - It never takes that slot from another package's script, such as pfBlockerNG's
    `pfb_unbound`.
  - Removing Sinkhole restores the previous Python settings.
- While Sinkhole is enabled, Bypass has at least one valid selected interface and Discovery
  isn't Off, Sinkhole keeps this managed block at the end of the DNS Resolver's Base64-encoded
  `unbound/custom_options` value:

  ```text
  # Sinkhole: begin (managed by the Sinkhole package)
  server:
  local-zone: "_dns.resolver.arpa." transparent
  # Sinkhole: end
  ```

  - The transformer preserves every administrator-owned byte and line ending, collapses
    duplicate blocks and repairs an incomplete block without consuming unknown lines.
  - Discovery Off, no selected Bypass interface, General Enable off, integration disablement
    and package removal all remove the block. Removal does so whether Keep Settings is on or
    off.
  - A changed block is written with `write_config()` and uses the same
    `services_unbound_configure()` path as Python-setting changes. An unchanged block creates
    no additional configuration revision or Resolver restart.
- Scopes are a hierarchy: global, then VLAN, then device.
  - A VLAN gets the global lists plus its own, and a device gets its VLAN's lists plus its
    own.
  - Each level can allow specific domains.
  - Devices are identified by IP address, DHCP static mapping or MAC address.
  - The VLAN level is a network: one pfSense interface. A client is on a network when its
    address is in one of that interface's IPv4 or IPv6 subnets, so a device that moves
    between networks gets the lists of the one it's on.
  - A device is the set of addresses it has right now:
    - an IP address device: that one address
    - a static mapping device: the mapping's configured address plus its MAC's current
      addresses
    - a MAC address device: its current addresses from the ARP and NDP tables and the DHCP
      leases
  - For each query, the most specific level decides, in this order:
    1. the device's allowed domains
    2. the device's lists
    3. the network's allowed domains
    4. the network's lists
    5. the global allowed domains
    6. the global lists
  - So a level's allowed domains let a name through every list it inherits, but not the
    lists of a more specific level.
  - A client that matches no network or device gets the global level.
  - A list is downloaded once and can apply to any number of scopes.
  - Interface subnets and device addresses live in a client map, kept apart from the
    compiled lists. A background job rebuilds it every minute and Sync launches that job
    only while DNS blocking has an enabled network or device scope, or Bypass DNS
    protection needs client matching. Turning every Sinkhole feature off removes the runtime
    map and its RAM-disk mirror on the next Sync. The module watches the map like the lists,
    so an address change never recompiles lists or reloads Unbound.
  - When two devices claim one address, the device listed first wins, and Status shows the
    conflict.
- Blocked names answer with `0.0.0.0` / `::`. The answer owner is reconstructed from the
  query's wire-format name with DNS presentation escapes, so every valid label byte,
  including spaces and bytes above `0x7f`, receives the same answer instead of SERVFAIL.
- A response whose CNAME chain reaches a blocked name is blocked too, as AdGuard Home and
  Pi-hole do by default. An allowed query name stays allowed.
- Unbound never serves a listed name from its cache, so a cached answer can't skip a
  client's scope.
  - The module sets `qstate.no_cache_store` for listed query names.
  - It also sets `qstate.no_cache_store` from Unbound's query-response callback
    (`register_inplace_cb_query_response`) whenever an upstream response has a listed owner
    in its answer or additional section, so a CNAME chain through a listed name is never
    stored. The iterator runs that callback before it stores anything from the response.
  - When an answer assembled from cache still reaches MODDONE with a listed owner, the module
    expires it there (`invalidateQueryInCache`). Expiry alone isn't enough, because the DNS
    Resolver's Serve Expired option answers from expired entries.
  - After a deploy that adds names or extends a name to its subdomains, a background job
    waits for the module to load the new generation, then reloads Unbound once
    (`unbound-control reload`), which empties its cache, so names cached before they were
    listed are dropped. `flush_zone` isn't enough: it only marks entries expired, and Serve
    Expired keeps answering from them. The reload stays owed until a background job
    completes it, whichever path deployed. The WebGUI never waits for this.
  - Released Unbound ignores the return value of reply callbacks (only Unbound master
    after 2026-10-20 honors it), so the module never relies on one to refuse a cached
    answer.
- Unbound reloads in-process often on pfSense (DHCP lease registration, host overrides),
  and since Unbound 1.18 a reload re-runs the module in the same Python interpreter. No
  module thread outlives `deinit`, and a reload reuses the data already in memory.
- The module notices new data through its own watcher thread, so loading never depends on
  DNS traffic or delays a query.
- Accepted list formats: hosts files, plain domain lists and supported adblock-style
  `||name^` domain rules.
  - Hosts-file and plain-domain entries are exact: each blocks only its normalized name.
  - An adblock-style `||name^` entry is a subtree rule: it blocks its normalized name and
    every subdomain.
- The popular-list catalogs (AdGuard Home's list registry, pfBlockerNG's feed catalog) are
  fetched at run time and never bundled.
  - Sources: `https://adguardteam.github.io/HostlistsRegistry/assets/filters.json` (its
    `filters`, without deprecated ones), and the `dnsbl`, `ipv4` and `ipv6` sections of
    pfBlockerNG's `pfblockerng_feeds.json` from the `devel` branch of
    `pfsense/FreeBSD-ports`. Each page exposes only the source keys it owns.
  - Catalog searches live on the Lists, Bypass and IP pages. The catalogs download only
    when an administrator opens a search or refreshes it, never on a schedule, through the
    same download client and limits as lists. The last good copy of each is cached under
    `/var/db`, with its fetch time, and reused for a day. A failed fetch keeps the last copy
    and shows the error.
  - Catalog text is untrusted: it is validated, length-capped and escaped, and only
    `http`/`https` list URLs are offered.
  - Each result shows its name, description, source catalog and homepage, with no
    recommendation or rating. Lists creates an ordinary list that the administrator assigns
    to scopes, Bypass creates an enabled Bypass List with the catalog-fixed kind, and IP
    creates an ordinary IP list. A result whose URL is already configured on that page shows
    as added.
  - Results show as cards, grouped by a "Group by" switch:
    - Category (the default):
      - Ads and trackers: AdGuard's General group, and pfBlockerNG's EasyList, ADs, ADs_Basic, Firebog_Advertising, Firebog_Trackers and Compilation
      - Security: AdGuard's Security, and pfBlockerNG's Malicious, Malicious2, Phishing, Cryptojackers, Firebog_Malicious, Firebog_Suspicious, BBcan177 and BBC
      - Other services: pfBlockerNG's STUN, Skype_Resolvers, Torrent, URL_Shorteners and Email
      - Regional: AdGuard's Regional
      - Other: AdGuard's Other, pfBlockerNG's Firebog_Other, and any group not mapped yet
    - Maintainer: the homepage host without `www.`, or `github.com/<owner>` and `gitlab.com/<owner>` for those two hosts.
  - Category chips with counts follow the search, source and maintainer filters. A Maintainer menu lists maintainers by number of lists.
  - Each card shows the name, the maintainer or category (whichever isn't the grouping), the
    source, a two-line description, the homepage, and Add or Added. Bypass cards also show
    the fixed kind.
- Blocked services block whole brands per scope, from AdGuard Home's services registry
  (`https://adguardteam.github.io/HostlistsRegistry/assets/services.json`).
  - **Fetching:** like the catalogs, the registry is fetched on demand and cached under `/var/db` for a day, with the last good copy kept on failure. It's never bundled and never fetched on a schedule.
  - **Rules:** a service's `rules` use the adblock syntax Sinkhole already parses. Rules the parser doesn't accept are skipped and counted.
  - **Services tab:** after Lists. The administrator picks a scope (global, a network or a device) and switches services on. Choices are stored by service `id` under that scope.
  - **Compiling:** a scope's blocked services compile into the same data as its lists, at the same level of the decision order. Allowed domains still win, in the existing order. The compiled data keeps the rules from the last good registry copy, so blocking never waits on the network.
  - **Unknown ids:** a saved service `id` the registry no longer has stays saved and is shown for repair, as invalid list rows are.
  - **Bypass-owned ids:** a registry `id` covered by a Bypass protection is hidden from
    Services and dropped from saved selections instead of being shown for repair.
  - **Tiles:** grouped by the registry's `group` (streaming, social networks, gaming, AI, messengers and so on), each with the service's logo from `icon_svg`.
  - **Logos are untrusted:** each is drawn only as `<img src="data:image/svg+xml;base64,…">`, never as inline markup, and is size-capped. A missing or oversized logo shows the group's generic icon.
- IP and country blocking is a separate setting, off by default, on its own IP page.
  - IP lists are added by URL or from the `ipv4` and `ipv6` sections of pfBlockerNG's feed
    catalog, except for source groups owned by Bypass. They use the same search, download
    client, limits and last-good saved copies as DNS lists. Lines are IPv4 or IPv6 addresses
    or CIDR networks; anything else is skipped and counted, and a list with no valid entry
    keeps its last good copy. IPv4 networks broader than `/8` and IPv6 networks broader
    than `/16` are also skipped and counted. The IP Allowlist has no such floor because it
    can only reduce blocking.
  - Countries come from MaxMind GeoLite2 Country (the CSV download) with the administrator's
    own account ID and license key, stored like a pfSense password field and never logged
    or shown. The administrator picks countries by ISO code; their networks join the
    blocked set. The database updates weekly at most.
  - Blocked networks are merged, de-duplicated and written per family to files under
    `/var/db`, and an allowlist of addresses, networks or aliases removes entries from them.
  - The blocks live in a pf anchor, `sinkhole/ip`. The package's `filter_rules_needed` hook
    returns only `anchor "sinkhole/ip"` for its `pfearly` call, because pfSense places
    `pfearly` text ahead of its own and the administrator's rules, while `filter` text comes
    after them, behind pass-quick rules where a block never matches. The hook returns
    nothing for `filter`.
  - Sinkhole loads the anchor itself with `pfctl -a sinkhole/ip -f`: two persist tables
    filled from the per-family files, and `block drop in quick` rules on the interfaces the
    administrator picks. Inbound blocks packets arriving from a listed address (for a WAN);
    Outbound blocks packets arriving to a listed address (for client networks). Rules on
    `out` would only match traffic the firewall sends toward that interface's own network.
  - Anchor contents survive pfSense's filter reloads, and pfSense's post-load cleanup kills
    only main-ruleset tables that aren't aliases, so the anchor's tables stay. The update
    job, Sync and the per-minute check load or flush the anchor so that it matches the
    setting; a filter reload alone never empties it. Removal and turning the setting off
    flush it.
  - Every configured firewall interface address, every complete subnet of an interface
    selected for IP blocking, CARP and IP-alias virtual addresses, and every gateway and DNS
    server address, including ones learned from DHCP or PPP, are removed from the blocked
    sets before they're written, so they're never blocked. Nothing in the anchor passes
    traffic, because an early pass would override the administrator's own blocks. Status
    shows table sizes, the last update, skipped lines and errors.
- Country data comes from MaxMind GeoLite2 with the administrator's own account and license
  key. Never ship a key.
- Alerts fire only for the lists, VLANs and devices an administrator chose, and go out only
  through pfSense notifications.
  - An alert rule names its block lists (any list, or chosen ones) and its clients
    (everyone, or chosen networks and devices). A block matches a rule when one of the
    lists that blocked the name is the rule's and the client is the rule's.
  - Only blocked answers raise events, and only when an enabled rule matches. The module
    queues matching blocks in memory, and its watcher thread appends them to an event file
    in `sinkhole-state`, so DNS never waits on a write. The queue and the file are bounded;
    when either is full, new events are dropped and counted.
  - A per-minute job, installed only while an enabled rule exists, reads the events as
    untrusted input and deletes what it read. It notifies once per rule, client and domain
    within the rule's repeat window (60 minutes by default). Sinkhole keeps no other block
    history.
  - Delivery uses pfSense's own channels, chosen per rule: a WebGUI notice (`file_notice()`
    with its local-only flag) and the configured remote services (`notify_all_remote()`).
  - One run sends a bounded number of notifications, and the rest of a burst folds into one
    summary per rule, so a burst can't flood an inbox.
  - Each rule also sends at most 60 notifications an hour; past that, the rest of the hour
    folds into one summary. The WebGUI holds at most 50 unread Sinkhole notices; past that,
    Sinkhole adds none until some are read, and Status counts what it held back.
  - The module folds identical blocks (same client, name and rules) within one watcher tick
    into one event with a count, so one chatty name can't crowd out the rest.
  - Events older than 10 minutes are dropped as stale. When no enabled rule is left, the
    event file and the repeat state are deleted.
  - Removal never waits on the alert job past its lock timeout, and always restores the DNS
    Resolver. A run that goes past its time budget leaves the remaining sends for the next
    run.
- Nothing rewrites files under `/cf/conf` on a schedule. Status that changes every minute
  lives under `/var/run`, and markers and repeat state are written only when their content
  changes.
- The plain-DNS redirect is a Bypass setting that stays off until an administrator turns it on.
  - It applies to the one interface selection shared by the Bypass page. On each interface, NAT sends DNS (TCP
    and UDP port 53) that isn't addressed to the firewall to the local DNS Resolver.
    Clients keep their own source address, so their scope still applies, and the
    Resolver's access control has to allow their networks, as it does for direct queries.
  - The redirect targets are addresses the Resolver listens on:
    - IPv4 goes to 127.0.0.1 while the Resolver listens on localhost, and otherwise to the
      interface's own IPv4 address.
    - IPv6 goes to the interface's own IPv6 address, never ::1. FreeBSD drops a packet whose
      destination pf rewrote to ::1 when it arrived on another interface.
    - The Resolver listens on every address when its Network Interfaces setting is All.
      Otherwise it listens on localhost if that is selected, plus each selected interface's
      own IPv4 and IPv6 addresses. A family whose target the Resolver doesn't listen on gets
      no rule, and Status says why.
  - Exempt sources (addresses, networks or pfSense aliases) keep reaching other resolvers.
    Exempt destinations (the same kinds) keep receiving DNS, such as an internal DNS server
    on another network.
    - Each exemption list becomes one `no rdr` line per address family, with an explicit
      `inet` or `inet6`, and an alias appears in both. pf keeps only the first address
      family of a mixed list, so a mixed line silently drops the rest.
  - An exemption that is no longer valid, such as a renamed alias, pauses the whole redirect
    until it's fixed, because an exemption promises a device its own DNS. Status shows the
    value, and Sinkhole logs it once.
  - The rules come from the package's `filter_rules_needed` hook through pfSense's
    `discover_pkg_rules()`, so pfSense checks them with `pfctl -nf` and drops them on an
    error. Sinkhole adds nothing to the firewall configuration, so removal leaves nothing
    behind after a filter reload.
  - pfSense writes `/tmp/rules.packages.sinkhole` when it rejects the rules and never deletes
    it. The hook deletes a leftover file at the start of its NAT call, so the file only
    describes the latest reload. The rules count as loaded when the latest
    `/tmp/rules.debug` holds exactly the text the hook returns now; Status shows the kept
    parse error only while Sinkhole's block is missing, and says when the loaded block is
    out of date. Removal deletes any leftover error file after its final reload.
  - The rules exist only while Sinkhole is active, meaning the DNS Resolver is enabled, is
    running and runs Sinkhole's module. Otherwise the hook returns none.
  - pfSense's DNS Resolver page reloads no filter when the Resolver stops or changes its
    Network Interfaces. So while the redirect is on, a per-minute check reloads the filter
    when the loaded rules and the wanted rules have disagreed on two checks in a row. A
    different text counts as a disagreement, so a stopped Resolver swallows redirected DNS
    for about two minutes at most, a changed target applies within about two minutes, and a
    Resolver restart never flaps the rules.
    - The check doesn't reload while pfSense's package lock is held, because pfSense skips
      package rules then. It also doesn't reload while pfSense's latest rejection was of the
      same text the hook returns now; it logs that rejection once.
  - Installing or upgrading writes the configuration and then, while the redirect is on,
    reloads the filter. The reload sees the hook that pfSense registered in memory, and a
    new version's rule text applies at once.
  - DNS over TLS or HTTPS isn't redirected; only port 53 is.
  - Turning the redirect on or off, or changing its interfaces or exemptions, reloads the
    filter. Removal does too.
- Bypass Protection is an independent, explicitly opt-in rule group on the Bypass page.
  - Bypass owns every bypass method. Bypass feeds appear only in the Bypass catalog, and a
    service covered by a Bypass protection is hidden from Services.
  - Every checkbox is off, Discovery is Off, no interface is selected and no Bypass List
    exists on a fresh configuration. An upgrade preserves the existing redirect settings
    and interfaces but never enables another protection or creates or enables a Bypass List.
  - One **Apply to** interface selection is shared with the plain-DNS redirect. Every Bypass
    protection applies only to traffic arriving from clients on those interfaces, or to DNS
    queries from clients in those interfaces' subnets. The firewall's own DNS lookups and
    outbound traffic are never affected.
  - Bypass client matching reuses the interface-subnet data that network scopes put in the
    client map. There is no second interface or client resolver.
  - **TLS and QUIC** blocks arriving TCP and UDP port 853 traffic to destinations other than
    the firewall.
  - **Providers**, **Tor** and **VPN providers** each use enabled Bypass Lists of the matching
    Encrypted DNS, Tor or VPN kind:
    - A list accepts one mixed domain, IPv4 address, IPv6 address or CIDR per line. `#` starts
      a comment. The existing bounded domain and IP normalization rules are reused, and every
      source is treated as untrusted.
    - Enabled rows fetch on the existing list schedule through the same bounded download
      client. Each row keeps normalized data and fetch/error status, and a failed download
      retains the last good copy.
    - Names compile into the module's Bypass data and are blocked only for clients on selected
      interfaces while that kind's protection is on. Existing allowed-domain decisions win
      over these list-name blocks.
    - Addresses and CIDRs join per-family persist tables and are blocked on every port and
      protocol for traffic arriving on selected interfaces. Firewall-interface, gateway and
      DNS server addresses, including ones learned from DHCP or PPP, are subtracted before
      the tables are written, so the firewall itself is never a listed destination.
  - The Bypass catalog reads AdGuard Home filters whose stable `filterKey` contains `bypass`
    and pfBlockerNG's `dnsbl` `DoH`, `ipv4` `DoH_IP`, `TOR`, `VPN_4`, and `ipv6` `DoH_6`,
    `VPN_6` groups. Each source key fixes the created Bypass List's Encrypted DNS, Tor or VPN
    kind; the catalog never classifies by URL.
  - **Firefox** answers `use-application-dns.net` and its subdomains with NXDOMAIN for selected
    clients. **Private Relay** answers `mask.icloud.com` and `mask-h2.icloud.com` with NXDOMAIN.
    Allowed domains never override these signals.
  - **Discovery** handles `_dns.resolver.arpa` for selected clients before allowed domains:
    - Off leaves the query untouched.
    - Answer with no records returns NOERROR with an empty answer.
    - Advertise returns an SVCB record that points at the firewall's DNS-over-TLS certificate
      hostname on port 853 with `alpn=dot`. Saving this mode fails unless the DNS Resolver's
      SSL/TLS service is enabled and supplies a usable certificate hostname.
    - Either active mode installs the managed transparent local-zone block defined in the DNS
      Resolver rules above so the Python module receives the query. The block remains absent
      when Bypass, Discovery or Sinkhole is inactive.
    - With Discovery active, the module answers clients outside the selected interfaces and
      internal queries with NXDOMAIN, matching Unbound's default locally served zone, and keeps
      `_dns.resolver.arpa` out of the cache. Discovery Off continues to pass the query.
  - **Standard VPN ports** blocks arriving OpenVPN TCP and UDP 1194, WireGuard UDP 51820,
    IPsec UDP 500 and 4500, and ESP to destinations other than the firewall.
  - Bypass firewall rules and tables live only in `sinkhole/bypass`. The `pfearly` hook
    references that anchor independently from `sinkhole/ip`; Sinkhole loads it with
    `pfctl -a sinkhole/bypass -f`, records a digest, treats empty mixed rule/table listings as
    an absent anchor, and reloads it after settings, updates, Sync or a filter-reload mismatch.
    Its tables survive the main-ruleset cleanup. Disabling firewall protections flushes the
    Bypass anchor without touching `sinkhole/ip`, and disabling IP blocking never touches
    `sinkhole/bypass`.
  - Status reports every protection, whether the Discovery local-zone directive is present
    while Discovery is on, the Bypass anchor's loaded/current state, rule and table counts,
    and every Bypass List's entries, last fetch and error. Removal flushes the anchor, removes
    the managed Discovery block, and removes cached Bypass Lists, compiled Bypass data and
    generated tables; saved settings follow the existing Keep Settings rule.

#### Updates

- GitHub release checks run independently of list/IP updates on a stable randomized Daily,
  Weekly, Monthly or Never schedule. Weekly is the default; Never disables only the scheduled
  check, so the About page can still check manually.
- Each newly available version creates one pfSense bell notice. `file_notice()` remains local to
  the firewall unless the user explicitly enables remote update notifications, which are off by
  default.
- The About tab provides Check Now and, when appropriate, Update to `<version>`. Self-update runs
  the CLI detached and the page polls private status state until the operation succeeds or fails.
  The About privilege remains read-only: both actions are hidden and rejected server-side unless
  the logged-in user has `page-firewall-sinkhole-general` or `page-all`, checked with pfSense's
  `getUserEntry()` and `userHasPrivilege()` helpers.
- Release assets must use the exact
  `https://github.com/mrjackyliang/pfsense-sinkhole/releases/download/` prefix. The updater uses
  the GitHub API SHA-256 digest when present or the exact hash-only `.sha256` asset otherwise,
  caps packages at 64 MiB and checksum/signature assets at 64 KiB, holds the package `FileLock`,
  and installs only with `pkg add -f`.
- The updater reads `release-signing.pub` from `DATADIR`. A missing or comment-only key list keeps
  unsigned releases compatible. Once the installed list contains Ed25519 keys, the matching
  `<pkg>.sig` asset is mandatory and `/usr/bin/ssh-keygen -Y verify` must validate the package with
  principal and namespace `pfSense-pkg-Sinkhole` before `pkg query -F` reads package metadata.
- CLI test overrides may replace only the release API and trusted download prefix. They never
  replace the installed signing-key path. Release signing belongs to Nova's pfSense publish target,
  which appends the public key and uploads `.sig`. Until a published Nova ships that target, the
  separate `.github/workflows/pfsense-sinkhole.yml` carries the same two steps (add the key to the
  staged `release-signing.pub`, sign each `.pkg`) with the `PFSENSE_RELEASE_SIGNING_KEY` secret.
  The signing namespace is the file name minus a trailing `-<version>` part, so both the versioned
  package and the stable `pfSense-pkg-Sinkhole.pkg` copy are signed as `pfSense-pkg-Sinkhole`. The
  updater downloads only the versioned package and its `.sig`.

pkg add -f https://github.com/mrjackyliang/pfsense-sinkhole/releases/latest/download/pfSense-pkg-Sinkhole.pkg

The `-f` is required because pfSense 2.8's pkg 1.21.3 otherwise skips an update from the

pkg delete -f pfSense-pkg-Sinkhole

repository do not appear on pfSense's Installed Packages page, so no WebGUI uninstall button
